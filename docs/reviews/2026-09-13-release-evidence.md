### 3.3 The finding, and the narrow fix — `f27219f`

After the accepted backdated post, the composer kept **2026-09-12** while
everything else cleared. A date that is not today's stamp counts as work
(D349), so the next save wrote a **date-only draft** — `vals` all empty but
`inDate:"2026-09-12"`, `touched:false`, `plan:null` — and every later load
restored it, re-saved it and announced a returned round. The composer defaulted
to yesterday until Start over. The cause was an asymmetry with no product
reason: `resetPostComposer` restamped, `clearPostComposerAfterPost` did not,
while the phone does `day = Date()` after posting.

Fix: `clearPostComposerAfterPost(){ putTheCardDown({ restamp: true }); }`, with
the stamp refreshed before the draft is cleared so a save fired by the clearing
finds nothing to keep. Regression in `tests/after-golf-repairs-browser.js`:
posts a backdated round through the real button against a stubbed server, then
asserts the date is today, no draft is written, and a reload restores nothing.
**It fails on the previous code** with "the posted date stayed on the form"
(run and observed) and passes on the fix, at 390 and 320.

Re-verified live on `f27219f` with the review profile: the phantom written by
the earlier build was still stored (the fix prevents new ones; it does not
sweep old ones), one real **Start over** cleared it, and a reload then restored
nothing — `formDate` today, `draftStored:false`, `gross:""`, `plan:null`. On
`963d0e6` the same read: `phantomStillStored:false`.

**Residue, stated:** a browser that already holds a date-only draft from the
window when `985d99c` was live (15:xx–15:56 today) keeps it until that golfer
taps Start over once. No sweep was added; that is a product call, not a hotfix.
